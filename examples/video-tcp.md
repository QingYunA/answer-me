---
title: TCP 三次握手
subtitle: 为什么是三次，而不是两次
---
> 两台机器要用 TCP 聊天，得先确认一件事：对方真的听得见、也说得出话。

## 两端都在等待
```sequence
Client -> Server: SYN
Server -> Client: SYN-ACK
Client -> Server: ACK
note Client, Server: ESTABLISHED
```
> 先是客户端开口，发一个 SYN，意思是"我想跟你建个连接"。
> [Server] 听到了，回一个 SYN-ACK："收到，我这边也没问题。"
> 客户端再回一个 ACK，说"好，那就开始吧"。
> 三句话说完，两边就都进入了 ESTABLISHED 状态。

## 每一步确认了什么
```flow LR
Client -> Server: 第一次：客户端能发
Server -> Client: 第二次：服务端能收能发
Client -> *双方确认: 第三次：客户端能收
```
> 我们换个角度看，每一次握手到底证明了什么。
> 第一次，服务端知道了：客户端能发出消息。
> 第二次，客户端知道了：服务端收得到，也发得出。
> 可还差一件事。直到第三次，服务端才确认 [客户端能收]。

## 如果只握手两次
| 情况 | 两次握手 | 三次握手 |
|---|---|---|
| 旧的 SYN 迟到 | no 服务端误建连接 | ok 客户端不回 ACK |
| 资源浪费 | no 空等的连接 | ok 不会建立 |
| 双向确认 | warn 只确认一半 | ok 完整确认 |
> 那只握两次行不行？我们设想一个场景。
> 一个很早发出的 SYN，在网络里绕了半天，现在才到。
> 如果只握两次，服务端会当真，开好连接干等，白白占着资源。
> 握三次就不一样了。客户端一看不对，不回 ACK，这个连接也就建不起来。
